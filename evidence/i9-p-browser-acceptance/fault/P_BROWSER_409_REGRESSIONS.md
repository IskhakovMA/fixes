# Независимая проверка восстановления реестра и сессии в B1

Проверен чистый B1 `3a0cb5db434032b3f7b6370c305c558a4b5d331c`. Прошли три существующих набора Chromium + реальный FastAPI + временная синтетическая SQLite: реестр на 1000 карточек, черновики на 100 и Quality на 240. Эти прогоны проверяют корректность поведения, включая конкуренцию. Для замера естественной частоты конфликтов нужен отдельный поток Pilot P.

| Сценарий | Что наблюдалось | Как создано событие |
|---|---|---|
| `PATIENT_QUERY_CHANGED` при изменении карточки и при отдельном техническом COMMIT | Автоматически только одно чтение. После 409 вторая страница не остается видимой, UI восстанавливает актуальную первую страницу. Два 409 завершают автоматическое обновление. Затем работает явное обновление. | Серверная синтетическая инъекция SQLite COMMIT в контрольной точке, реальный ответ FastAPI. |
| Потеря сессии и версия черновика | Настоящий 401 после завершения сессии. После входа и обновления реестра остались прежнее намерение, версия и разрешенный выбор. Ручная попытка сохранить старую версию получила 409, состояние сервера не перезаписалось. | Реальные API двух независимых сессий. |
| Реальная смена разрешений в Quality | 401 и access-context 409 запирают старую сессию, удаляют старые строки и не запускают автоматическое обновление списка. После reauth применяется новый scope. При смене лечащего врача объектный 404 очищает открытую карточку, производные строки и черновик. | Вторая сессия выполняет обычное администрирование синтетической фикстуры. |
| Запоздалый ответ после другого результата или смены личности | Удержанный реальный 200 не восстанавливает старые строки или данные прежней личности. Запоздалый отказ прежней сессии не запирает новую. | Браузер удерживает реальный ответ и отдает его при контролируемом порядке событий. |
| Ошибки на уровне UI transport | Отдельные сценарии инъецируют 410, 503, 401, access-context 409 и отказы Quality. | Подмена HTTP-ответа в Playwright. Эти сценарии не доказывают первопричину серверного 503. |

У браузерных страниц, проверявших роли реестра, счетчики legacy full-list и медицинских записей равны нулю. Тест сверил SHA-256 аудита для успешных выдач в синтетическом стенде. Реестр прошел 24 проверки axe на шести ролях, Quality прошел шесть комбинаций темы и ширины. Это отдельный автоматический результат Chromium, ручная D8 Safari/VoiceOver сохраняет свой статус.

Первичная инфраструктурная попытка не дошла до браузерных сценариев: Playwright ожидал другой номер локальной сборки. Сохранены исходные журналы. Финальные прогоны использовали явно указанный установленный Chrome for Testing `153.0.8010.12`. Тесты точного B1 не редактировались. Полные локальные журналы, снимки и исходные браузерные данные не входят в публичный пакет.

## Отдельное наблюдение по клавиатуре после второго 409

Фокус установлен на штатную кнопку пагинации, отправлено обычное нажатие Enter через Playwright. Инъекция создает COMMIT на сервере и реальные ответы B1. Первый сценарий прошел 409 → 200 с возвратом фокуса на статус первой страницы. Во втором сценарии 409 → 409 область старой выдачи скрылась, состояние ошибки стало видимым, фокус не остался внутри старых результатов. Отдельный тест ожидал переход на «Обновить список». Первый Tab не установил этот фокус. В повторной диагностике фокус не дошел до кнопки за 60 Tab в локальной конфигурации headless Chromium. Во время этого дополнительного обхода сервер увидел еще один GET, его источник не доказан. B1 отдельно перечитывает состояние при событиях focus/visibility. Штатный сценарий без дополнительных Tab ранее подтвердил ровно две попытки и ручное восстановление кнопкой.

**Severity: средняя, влияние на клавиатурное управление и доступность.** Медицинских утечек, повторной записи и восстановления старого состояния в этой проверке не зарегистрировано. Клавиатурная диагностика завершилась открытым замечанием. Итоговые численные тайминги этой пары не сохранены из-за остановки по assertion. Результат не используется для оценки естественных 409 или UX SLO. Показатели основного браузерного шейкдауна хранятся отдельно.

В B1 загрузка делает результаты реестра inert, а терминальная ошибка скрывает их. Кнопка пагинации находится внутри этой области. Обработка успеха явно возвращает фокус на статус страницы. Терминальный catch публикует toast без передачи фокуса. Кнопка явного обновления находится в видимой соседней области и в DOM предшествует пагинации. Этот код объясняет отсутствие явного handoff. Причина всей наблюдаемой Tab-последовательности и влияние сторонних событий фокуса остаются предметом отдельной проверки.

Предложен [изолированный патч только фокуса](P_BROWSER_409_PAGER_FOCUS_PROPOSED.diff.patch), **UNVALIDATED**. Патч делает handoff к видимой кнопке явного обновления только для ошибки `PATIENT_QUERY_CHANGED` в актуальном запросе, когда породивший действие pager владел фокусом, браузерный документ все еще активен, фокус потерян и отсутствует новая сессия или диалог. Ручное решение о повторе сохраняется. Проверены применимость к точному B1 и синтаксис; на модифицированном приложении браузерный сценарий не запускался. Навигация, запросы, медданные и B1 не менялись. До решения об интеграции нужен отдельный браузерный прогон с двумя 409, переходом в другую область и сменой сессии во время запроса.

Для диагностического повторения на временной синтетической базе используйте `run_p_browser_409_timing.py` с чистой копией B1, новым внешним каталогом результатов, фиксированным Playwright и установленным Chromium. Скрипт может завершиться ненулевым статусом на наблюдаемом клавиатурном сценарии. Собранные исходные журналы остаются локально.
