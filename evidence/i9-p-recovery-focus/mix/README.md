# Pilot P — непустой консилиум и селективный фильтр

Короткий диагностический шейкдаун на чистом B1 `3a0cb5db434032b3f7b6370c305c558a4b5d331c`. Реальный FastAPI, SQLite v33, Chromium, собственный browser context каждой сессии. Публикуются агрегаты и инструмент. Исходные ответы, служебные ID, приватные fixture-файлы и журналы остаются локально.

## Фикстура и проверка

- Синтетические 1 000 пациентов. Ровно половина каждой области на этапе `exam`, половина на `treatment-prep`. У врача разрешено 160 карточек, у заведующего 800, у разработчика 1 000. Отбор дает соответственно 80, 400, 500. Прямой реальный HTTP для каждого проверяет фактический список на страницах offset 0 и 50, наличие или конец cursor, отсутствие чужих карточек, целостность `summary.total` и `summary.inTreatment`. Специальный facet вне отделения виден только в широкой области разработчика, у врача и заведующего его нет и при фильтрации. В нагрузочной смеси проверяются также идентичность видимых строк с ответом и сохранение селективного фильтра при восстановлении после 409.
- Три реальные синтетические записи консилиума созданы через существующие сервисы расписания, записи, рассмотрения, возврата и повторной подачи. Состояния `revised`, `needs_revision` и `recorded`; фикстура содержит четыре строки истории возвратов и три повторные подачи, ни одной подписи. Врач и заведующий видят по две записи, разработчик одну собственную, председатель три. Для врача, заведующего и разработчика проверен реальный нейтральный 404 на чтении истории записи вне доступа. У разработчика и председателя два раунда в разрешенном HTTP и в видимой панели после клика.
- Чтение и рендер консилиума проверены при обоих режимах с непустым содержимым, точными статусами и версиями. После полного прогона SQLite подтверждает точное совпадение набора актуальных статусов, версий, подписи, строк возвратов и повторных подач, успешных операций консилиума и этапов пациентов с исходным логическим снимком. Разрешенные PATCH касались только одного поля возраста одной синтетической карточки.
- Начальные сбои preflight сохранены отдельно: при первом 4-сеансовом запуске технический запрос попал в еще незавершенный переход на реестр. В первом 8-сеансовом запуске ожидание только `ready` не обрабатывало фактическое состояние `error`. Инструмент теперь ждет завершения старого перехода и, при видимой ошибке, выполняет ровно одно явно отмеченное нажатие кнопки восстановления до warmup. Это не входит в знаменатель нагрузочного окна и не меняет его расписание.

HTTP 503 и timeout не наблюдались. В обоих режимах подтверждены восемь клинических COMMIT и их аудит с учетом warmup, из них по шесть в измеряемом интервале. Незапланированных медицинских записей не обнаружено. Основное медицинское чтение и отдельные preflight-ответы сопоставлены с durable audit/manifest по автору и SHA-256 полученного тела.

## Воспроизведение

Используйте отдельный чистый checkout exact B1, версию Python 3.13 из закрепленного окружения, установленный Chromium соответствующего Playwright и loopback-only. Команда создает новый приватный каталог синтетической БД и очищает его по завершении. Каталог результатов должен находиться вне Git.

```sh
for mode in 4 8; do
  "$B1_PYTHON" -I -B p_run.py --repo "$B1_CHECKOUT" --out "$PRIVATE_DIR/mix-${mode}" \
    --node "$NODE" --playwright "$PLAYWRIGHT_MODULE" --browsers "$PLAYWRIGHT_BROWSERS_PATH" \
    --mode "$mode" --seconds 12 --warmup 4
  node browser_p_audit.cjs "$PRIVATE_DIR/mix-${mode}/driver.json"
done
```

Прогоны короткие, по 12 секунд измерения и 4 секунды warmup. Профиль подачи и доли ролей те же. Изменились состав фикстуры, проверка содержимого и время окна. Исторические 83,3% и 81,7% сохранены как предыдущий шейкдаун. Эти измерения не дают основания считать изменение результатов эффектом фикстуры и не подтверждают 98%, UX SLO или готовность к эксплуатации.
