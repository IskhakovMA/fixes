# Пересчет естественных 409 из двух исходных окон B1

Точный продукт `3a0cb5db434032b3f7b6370c305c558a4b5d331c`. Этот пересчет использует исходные приватные квитанции двух 20-секундных окон и не объединяет их с новым harness или контролируемыми инъекциями. Базовый инструмент и результаты закреплены в [предыдущем evidence](https://github.com/IskhakovMA/fixes/tree/3bc3d749462a80c21ed8e1e48bfe4f45afa54c28/evidence/i9-p-browser-acceptance).

Повторный 200 не меняет результат первого HTTP. UI считается готовым только когда опубликованные инструментальные утверждения сопоставили видимый DOM с актуальным разрешенным ответом. Терминальная ошибка, скрытый старый список и слоты busy остаются в знаменателе. После двойного 409 сотрудник видит ошибку и явную кнопку восстановления. Готовые данные в 17 восстановленных случаях появились без действий сотрудника. Порог 98% для первой метрики остается **PROPOSED**. Для вывода о длительной нагрузке эти окна и 9/11 естественных конфликтов недостаточны.

Фактические роли и размер scope различались вместе с длительностью защищенных чтений, ротацией врачей и совпадением слотов. Роль и ширина scope поэтому не являются независимо оцененными причинами. Расписание PATCH было периодическим с фиксированной фазой короткого блока, это допускает корреляцию с GET; отдельного измерения чувствительности к фазе или writer-off в этих записях нет.

## Механизм и причинность

B1 возвращает один и тот же `PATIENT_QUERY_CHANGED` для расхождения ревизии курсора, изменения полного fingerprint при повторной валидации и изменения `data_version` между валидацией и защищенным выпуском. Последний вариант реагирует на коммиты в БД в узком интервале, включая подходящие технические коммиты. Полный fingerprint включает разрешенную выдачу, сводку и версии объектов, в том числе за пределами выбранной страницы. Поэтому редкая запись может пересечь несколько одновременных release, а использование курсора может выявить коммит, который уже завершился до начала запроса следующей страницы. [Серверный механизм](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/backend/app/read_access.py#L123-L154) · [Полный fingerprint](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/backend/app/patient_pages.py#L177-L201)

В 11 из 20 случаев был cursor. Еще девять — чтения без него. Интервал HTTP клинического PATCH пересек HTTP интервал первого GET только в двух случаях. В 17 случаях ближайший по метке ответа PATCH уже получил ответ до отправки GET. Это сравнение HTTP‑времен, без серверных времени COMMIT и промежуточных снимков, и оно не различает причину конкретного отказа. Наблюдаемый общий код и момент запроса не дают оснований установить, какой именно коммит или ветка сгенерировали конкретный 409. Среди **естественных** случаев подтвержденно клинических 0, технических 0, происхождение не установлено у 20, ошибок классификации финальных runs нет. В отдельных диагностических ранее контролировались реальные клинические и технические изменения. Их счетчики с естественными случаями не объединены.

[20 обезличенных строк](P_409_NATURAL_RECOUNT.json) содержат роль, scope, вид действия, наличие курсора, HTTP‑окна, ответ повтора и конечный UI. Точное значение фильтра, исходный индекс страницы и время COMMIT проставлены как неизвестные там, где harness их не записал. Повторный пересчет доступен в [recount_natural_conflicts.py](recount_natural_conflicts.py).
