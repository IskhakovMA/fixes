# I-9 — предложение эксплуатационных профилей

**PROPOSED.** Рассматривается точный продукт `3a0cb5db434032b3f7b6370c305c558a4b5d331c`. Прогноз фактической клинической нагрузки требует утверждения владельца. Размеры, численность, частоты и пределы ниже — проектные параметры будущей синтетической проверки.

## Что известно из проекта

- Планировщик ведет клинический маршрут, карточки, чек-листы, события, консилиум и внутренние уведомления. Управленческие чтения включают аналитику, качество данных и предусмотренные экспорты. [Бриф продукта](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/PROJECT_BRIEF_V2.md)
- Врач видит своих пациентов, заведующий — область управляемых отделений, разработчик выполняет администрирование и разрешенные операции по полной области. Руководящие роли могут иметь широкое read-only чтение. Председатель работает по собственному контракту консилиума. Запись пациента, управление сеткой и подписание разделены серверными правилами. [RBAC](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/RBAC_DESIGN.md) · [Политика консилиума](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/backend/app/policy.py#L256-L329)
- Страница реестра обычно 50, максимум 100 строк. Показатели и контроль выпуска могут затрагивать всю разрешенную область, включая строки за пределами фильтра и страницы. Поэтому для каждого замера нужны три размера: весь набор, авторизованный scope и активная выборка. [Серверная пагинация](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/backend/app/patient_pages.py)
- Поддерживаемая конфигурация запуска — один FastAPI server process на каталог SQLite, с контролируемым WP-F допуском. Число браузерных сессий, concurrent requests и число server workers измеряются отдельно. Несколько серверных процессов потребуют отдельного решения по общим защитным механизмам. Доставка уведомлений наружу и внешний AI в этих профилях выключены. [Операции](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/OPERATIONS.md) · [Runbook](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/PILOT_RUNBOOK.md#L30-L40)

## Документированные ожидания и пробелы

Прежнее pilot readiness review предлагает ограниченную группу одного отделения, контролируемый single instance, синтетические или обезличенные данные, назначенные роли, резервную копию и rollback. Оно описывает границы, но не дает утвержденного прогноза числа сотрудников, объема базы, нагрузки по маршрутам или числа сессий в смену. Оно отдельно указывает, что production load test не был проведен. [Документированный пилот](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/PILOT_READINESS_REVIEW.md#L29-L38) · [Границы производительности](https://github.com/IskhakovMA/fixes/blob/3a0cb5db434032b3f7b6370c305c558a4b5d331c/PILOT_READINESS_REVIEW.md#L286-L300)

Нет подтвержденных эксплуатационных счетчиков по сменам или согласованной инфраструктуры. 100, 1000 и 10000 карточек относятся к синтетическим методикам. 20% врачебного и 80% заведующего scope — свойства одной фикстуры, а не прогноз распределения в клинике.

## Три сценария для согласования

| Параметр | D — демонстрация | P — ограниченный пилот | X — расширенный |
|---|---|---|---|
| Полная синтетическая база | 100 | 1000 | 10000 |
| Активная рабочая выборка (плановый диапазон) | 50–100 | 100–300 | 500–2500 |
| Именованные операторы / одновременно активные сессии | 4–6 / 2–4 | 8–15 / 4–8 | 25–50 / 12–20 |
| Основные роли | Врач, заведующий, разработчик, наблюдатель. Председатель отдельно выполняет учебное заседание | Одно отделение, врачи и заведующий. Председатель в отдельной сессии планирования, руководство и разработчик с собственными правами | Несколько отделений, широкие head/read-only области, председатель и параллельная работа администрации |
| Предлагаемый минутный пик защищенного реестра и клинического PATCH | До 1 GET/с и 0,1 PATCH/с | До 3 GET/с и 0,5 PATCH/с | Рабочая граница для проверки 6 GET/с и 1 PATCH/с, отдельный stress 6/3 и серия 12/6,1 |
| Карточка и дополнительные рабочие потоки | 1 активное открытие/с в короткой волне, один инициатор записи | Короткая волна до 2 открытий/с одновременно с реестром. По отдельному сценарию одно клиническое действие и чтение расписания председателем | Короткая волна до 4 открытий/с. Выделить overlap последовательных записей двух независимых операторов, консилиум и отчет |
| Планируемая среда для замера | Один сервер, отдельная VM или рабочее место, синтетическая SQLite | Один сервер на утверждаемом профиле ресурсов, HTTPS reverse proxy в пилотоподобном стенде | Один сервер и SQLite до пересмотра архитектуры. Измерить дисковую нагрузку, задержки и резервирование до выбора мощности |

Частоты — предложенные слоты конкретных потоков, не суммарный HTTP RPS. Открытие карточки может вызвать несколько API-запросов. При принятии профиля нужно отдельно указать коэффициент этого fan-out, фоновые запросы и правило учета штатного контролируемого повтора. Один человеческий клик не равен одному GET. Создание, изменение, подписание и административная операция считаются раздельно. Никакие ошибочные клинические POST/PATCH автоматически не повторяются.

### Сценарии условной восьмичасовой смены

- **Врач:** начало смены и возврат после перерыва с обновлением реестра, несколько групп открытий карточек, заполнение событий/чек-листов и создание карт. Для моделирования D/P/X исходный диапазон на активного врача — 5–15 / 10–30 / 15–40 намерений открыть или обновить реестр, 10–30 / 20–60 / 30–80 открытий карточек, 0–2 / 1–5 / 2–8 созданий, 2–10 / 5–20 / 8–30 явных изменений. Эти числа — параметры симулятора. Временная волна задается отдельно, чтобы среднее за смену не занижало нагрузку.
- **Заведующий:** общее состояние отделения, спорные случаи, контроль качества и расписание. Добавить широкое scoped чтение независимо от видимых 50 строк, чтение чужой карточки с ожидаемым отказом и проверку отзыва доступа.
- **Председатель:** группы действий вокруг открытия заседания, запись назначенных сотрудников, перечитывание сетки, решение и архив. Предложение для сценария — 1 / 1–2 / 2–4 синтетических блока нагрузки за смену, с одновременными разрешенными чтениями и отдельными явными writes. Это число сценариев, а не расписание реального консилиума.
- **Руководство и администрирование:** в заявленном burst профиле запустить аналитику и доступные реестры. Отдельные пробы для больших отчетов и экспорта с сохранением SHA-256 manifest, действующих прав и лимитов. Включить один сценарий изменения права оператором и проверить, что старый ответ игнорируется.
- **Пик:** синхронный вход/возврат с перерыва, выдача реестра плюс периодические чтения и записи. Сохранять first load, steady state, задержки очереди, фактический dispatch, успешные клинические COMMIT и постоконный дренаж. 6/3 и 12/6,1 остаются открытыми стресс-сценариями. Ранее выявленная нулевая выдача широких ролей — ограничение для решения владельца, без исключения из анализа.

Для согласования владелец указывает охват отделений и ролей, отдельно размеры полной базы и scope, активные сессии в пике, доли типовых операций, рабочую нагрузку консилиума, требования к времени отклика и измеряемый стенд. Нужны обезличенные агрегаты по типам действий либо согласованные расчетные интервалы. Работа с реальными медицинскими данными в этом этапе не требуется. Для production отдельно утверждаются ресурсы хоста, защищенное хранение, HTTPS, RPO/RTO, backup и retention, операторские роли и incident process.
