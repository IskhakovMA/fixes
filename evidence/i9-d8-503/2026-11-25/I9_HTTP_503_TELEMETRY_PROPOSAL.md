# I‑9 · Предложение по диагностике будущих HTTP 503

**Статус предложения.** Исторические случаи объяснены 0/2. Существующая доказательная база подтверждает, что один HTTP-статус может возникнуть в разных фазах. Цель предложения — различить эти фазы при следующем наблюдении и установить, дошло ли подтверждение до границы приложения.

## Событие и корреляция

Сервис присваивает запросу случайный одноразовый ID до обработки. Этот ID не производен от сессии, пользователя, карточки, ключа идемпотентности или содержимого запроса. Для каждой повторной попытки нужен отдельный ID. Корреляция с возможным proxy использует ID из проверенной внутренней границы и отдельно учитывает статус приложения и конечного ответа proxy. Клиентский заголовок сам по себе доверия не создает.

Минимальная запись включает UTC-время, монотонный интервал, SHA сборки, метод и шаблон маршрута без параметров, статус приложения, безопасный прикладной код, фазу, класс контролируемого отказа и итог транзакции. Код SQLite добавляется только числом из разрешенного набора, когда он реально известен. Статус обязательного аудита и manifest фиксируется утверждением `committed`, `rolled_back`, `not_applicable` или `unknown`. Идентификаторы и содержимое этих записей для диагностики не нужны.

Предлагаемые границы наблюдения раздельны.

- Получена заявка на транзакцию, выполнен `BEGIN` или получен отказ захвата.
- `COMMIT` подтвержден, откат подтвержден либо итог неизвестен.
- Подготовка тела ответа, итог обязательного release audit, начало и завершение передачи со стороны ASGI.
- Наблюдаемая конечная передача proxy или разрыв соединения, если есть такой источник. Завершение ASGI не подтверждает прием всех байтов клиентом.

Устанавливать `committed` или `rolled_back` только на основании соответствующей успешно выполненной операции. При недоступности подтверждения оставлять `unknown`. Выход из хендлера и статус HTTP для вывода об исходе недостаточны.

## Границы безопасности и проверка

Поля события используют строгую схему, фиксированные значения и allowlist шаблонов маршрутов. Свободный текст исключений, SQL, медицинские поля, идентификаторы пациентов и сотрудников, query string, заголовки, содержимое ответа, тела запросов, токены и сырые HAR исключены из диагностической схемы. Записи доступны ограниченной роли, а правила срока хранения и доступа требуют отдельного утверждения. В публичные пакеты попадают только агрегаты и обезличенные синтетические квитанции.

Диагностика должна быть отделена от обязательного аудита. Запись метаданных не должна добавлять запросы к SQLite, удерживать транзакцию, вызывать повтор клинической записи или менять fail-closed выпуск. При отказе диагностического канала сохраняется обычное медицинское поведение. Потеря диагностического события учитывается отдельно.

Перед интеграцией проверить на синтетике отказ до захвата, откат записи, отказ обязательного аудита выпуска, успех COMMIT с ошибкой рендеринга, сбой передачи и истечение источника. Отдельно проверить redaction, состояние системы при заполнении канала, bounded overhead и отсутствие влияния на B1. Такой шаг требует решения владельца и отдельного review.
