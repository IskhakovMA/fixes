# Транзакционная безопасность медицинских операций I‑9

Проверено на синтетических данных из интеграции `f849b2909c2d23923e0ce996f0aca4b670ca9c18`.

- **SQLite writer contention до получения блокировки.** Отдельное соединение держит `BEGIN IMMEDIATE`. HTTP создание и изменение диагноза отклоняются с 503. В штатной проверке число строк при создании и снимок карточки при PATCH совпадают до и после. Это доказательство именно для проверенных транзакционных границ.
- **Устаревшая версия и mandatory write audit.** Штатные тесты проверяют конфликт ожидаемой версии и атомарность поля, истории диагноза и обязательного аудита. Защита от неполного сохранения проверена и при инъекции ошибки после изменений внутри транзакции.
- **Release audit и manifest.** Вставка аудита и manifest принадлежит транзакции защищенного чтения. При инъекции сбоя до COMMIT медицинский буфер удерживается. Пример некодированного 503 относится к транзакции выдачи, а не доказывает откат всех пользовательских операций.
- **Потеря квитанции после COMMIT.** Синтетическое исключение за границей транзакции дает HTTP 500, при этом в SQLite уже существует одна карточка. Повтор со старым ключом создания проверяет идемпотентность именно этого API. Отсюда не следует право на автоматический повтор медицинского PATCH. Если результат PATCH не подтвержден, перечитать карточку и ее версию по авторизованному каналу, затем принимать решение о повторе.
- **Граница выводов.** Ошибка настоящего SQLite COMMIT, оборванное TCP-подтверждение, серверные трассы двух исторических 503 и поведение реального браузера относятся к отдельным проверкам. Наблюдаемого неправильного медицинского сохранения в проверенных сценариях нет. Продуктовые изменения в SQLite, read release, пациентских страницах или общих тестах не вносились.

Независимые по фазе дополнительные контроли сериализации дали 503 без выпускного аудита и manifest для отказа перед release защищенного чтения и 500 с подтвержденными карточкой и аудитом для отказа JSON-рендера после COMMIT создания. У последнего повтора с тем же ключом 201 и прежний результат. См. `evidence/SERIALIZATION.jsonl`.
