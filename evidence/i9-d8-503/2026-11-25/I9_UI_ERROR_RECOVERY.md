# I‑9 · Восстановление интерфейса при отказах

База `f849b2909c2d23923e0ce996f0aca4b670ca9c18`, проверена по Git. Запуски используют локальный Chromium 151.0.7922.34, Node 22.23.4 и отдельную одноразовую синтетическую SQLite на каждый runner. Изменений приложения и CI нет. Ветка B1 не участвовала.

| Сценарий | Происхождение | Проверенный результат |
|---|---|---|
| 401 и изменение страницы 409 | Реальные responses FastAPI, WP‑H drafts | Черновик, выбранная карточка и базовая версия сохранены после повторного входа и смены снимка. Автоматической записи нет. Ручное сохранение устаревшей версии получает реальный 409 |
| 422 | Реальная валидация FastAPI, WP‑I card errors | Черновик остается. Повторное чтение подтверждает отсутствие изменения карточки |
| Кодированный 503 | Синтетический HTTP на перехвате PATCH с `SYNTHETIC_UNAVAILABLE`, WP‑I card errors | Черновик остается, автоматической отправки нет, состояние подтверждено отдельным GET |
| Потеря ответа после COMMIT | Реальный успешный PATCH 200 до искусственного разрыва, WP‑I card errors | Повторный GET подтвердил запись. Черновик сохранил исходную версию, автоматической отправки нет. Ручной запрос с этой версией получает реальный 409 |

При неизвестном результате записи безопасная операторская последовательность — сверить состояние свежим чтением и исходную версию, затем решать, нужна ли явная новая операция. Свежий GET в проверке был отдельным контрольным запросом, а не подтвержденным автоматическим сценарием интерфейса.

Первые три прогона не проверяли физический разрыв или буквальное озвучивание screen reader. Ниже приведены отдельные синтетические контроли этих серверно-транспортных границ. Потеря ответа после успешной записи здесь создана на транспортном уровне и не объясняет исторические 503.

Отдельный Quality browser на 240 синтетических пациентах прошел. Реальные 401 / 409 с изменением контекста приводят к блокировке, повторной авторизации и очистке прежних строк без перезапроса. Реальный owner 404 в той же сессии после изменения врача очистил карточку, строки и существующий черновик. Подставленные 403 и нейтральный 404 не оставляют доступных действий и не дают повторов. Подставленные 409/410 списка допускают один контролируемый перезапуск. Удержанный реальный 200 не перекрывает более новый результат или подставленный терминальный 503. Подставленный поздний транспортный отказ от прежней проверки личности не блокирует свежую сессию. Публичный Quality v1 дал ожидаемый прикладной 503 `QUALITY_NOT_AVAILABLE`. Сценарии 403 и нейтрального 404 в этом наборе проверяют реакцию UI и не подтверждают причины серверного отказа.

Команды с одной изолированной средой и фиксированными Node/Playwright/Chromium, запуск от корня проверенного worktree:

```sh
python tools/tests/wp_i_card/run.py --suite errors --out "$OUT/card-errors"
python tools/tests/wp_h/run.py drafts --out "$OUT/drafts"
python tools/tests/wp_i_quality/run_browser.py --suite browser --count 240 --out "$OUT/quality"
```

Во всех трех запусках exit 0. Машинные доказательства отобраны в `card-errors-sanitized.json`, `drafts-sanitized.json` и `quality-sanitized.json`. Квитанции D8 отсутствуют. Результаты доступны только для проверенного Chromium.

## Дополнительные Chromium-контроли

Отдельный WP‑I clinical прошел все девять проверок, включая инъекцию HTTP 503 с одним ключом `detail` для заметки и события, настоящий 404 при отзыве, изоляцию черновика при смене пользователя и отказ автоматической повторной записи. В контрольном прогоне с наблюдателем `probes/precommit-network-control.cjs` запрос PATCH прерван браузером до направления в FastAPI. Прошел ровно один перехваченный запрос, исходная версия и событие на сервере сохранены, черновик оставался в UI. Это модель потери сети до отправки. Она не подтверждает поведение маршрутизатора или Safari на устройстве.

## Back/Forward

Первый полный локальный браузерный прогон сохранил семь завершенных групп, в том числе восемь вкладок, отмену ухода с черновиком и восемь axe-состояний. Затем он завершился кодом 1 во время `transportAndIdentity` на `history.cjs:333`: Playwright не получил `networkidle` за 30 секунд после удержанного реального 200. Это другой участок, чем ожидание CSS из технического реестра. Состояние рабочей области в момент первого тайм-аута не измерено.

Отдельный адресный диагностический запуск на новой фикстуре сохранил прежние проверки и добавил обезличенного наблюдателя. В нем `networkidle` наступил, незавершенных запросов не было. Календарь оставался выбран, карточка скрыта, сессия действовала. Затем прошли потеря GET до получения ответа, реальный 401 и реальный 403 при смене сотрудника. Такой адресный PASS не отменяет исходный FAIL полного прогона. Причину расхождения не подтвердили. Для следующего исследования стоит сравнить завершение конкретного догоняющего браузерного чтения и авторизованное состояние DOM с сигналом всей сети, сохранив прежние assertions. См. `evidence/browser-navigation.json` и `evidence/HISTORY_TRANSPORT_OBSERVER.json`.

Повтор полной серии при подготовке публикации прошел. Траектория прошлого FAIL и результаты поздней диагностики описаны в [отдельной сверке](HISTORY_NETWORKIDLE_REVIEW.md).
