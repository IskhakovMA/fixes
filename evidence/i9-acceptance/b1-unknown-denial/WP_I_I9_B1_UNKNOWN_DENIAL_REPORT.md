## Причина

Проверка `unknownDenial` открывала уже видимую синтетическую строку через помощник, который одновременно заполнял поиск и сразу нажимал строку из исходного реестра. Поле поиска запустило отложенный GET. На Ubuntu запрос этого поиска начался на 708 мс, получил 409 на 752 мс, его штатный повтор получил 200 на 779 мс. На 847–870 мс наблюдался еще один запрос формы реестра с параметром поиска, попавший под одноразовый перехват. Проверки identity возвращали 200. После запуска поиска новых detail GET не видно. Playwright завершился на ожидании detail 404 в инструментированной строке 514, которая соответствует строке 472 точного B1. [Воспроизведение на Ubuntu](https://github.com/IskhakovMA/fixes/actions/runs/45662518534/job/139375845273)

После поискового 409 продукт выполняет один повтор и повторно сверяет доступ к открытым карточкам, включая черновики. На синтетическом контроле с заданным порядком событий первый поисковый 409 был подставлен на уровне транспорта после реального отзыва доступа. Штатный повтор и `GET /api/patients/resolve` обслужил реальный FastAPI. Scoped resolve вернул 200 без прежней карточки. Приложение очистило карточку, закрыло подтверждение и не получило нового detail 404, сессия оставалась активной. Тестовый сценарий пытался ждать именно ветвь с 404, которую безопасная ранняя очистка делает недостижимой. В узком исправлении устраняется посторонний поиск, чтобы тест дошел до требуемой реальной ветви отказа.

Hosted-наблюдатель не маркировал `/resolve` прямо и не записывал прикладной код поискового 409. Доказательство достаточности механизма дает локальный контролируемый сценарий. В первом историческом запуске доступны общий `browser:timeout` и точный SHA. Приписать его конкретной строке или writer SQLite по этому журналу нельзя. Несколько состояний диагностической трассы отфильтрованы, поскольку необязательные флаги приложения при конвертации дали `NaN` вместо ожидаемых двоичных меток. Вывод опирается на фактические HTTP-метки, стек Playwright, проверенный код и управляемый контроль. [Первый отказ](https://github.com/IskhakovMA/fixes/actions/runs/45657468106/job/139357897943)

## Изменения

- `.github/workflows/i9-v33-linux-browser.yml`. В проверочной ветке фиксирует родителей, область diff и точный checkout B1. Применяет History overlay только для `unknownDenial` и восстанавливает файл после него. Полная матрица из 18 jobs и 49 команд восстановлена после отдельного адресного прохода. Workspace block и каталог диагностических файлов сохранены побайтно.
- `tools/tests/wp_i_card/diagnostic/trace_unknown_denial.py`. Воспроизводит наблюдения на исходном тесте в адресном диагностическом коммите. Публикует только разрешенные технические метки через фильтр workflow.
- `tools/tests/wp_i_card/diagnostic/unknown-denial-harness.patch`. Временный overlay меняет один сценарий в `tools/tests/wp_i_card/history.cjs`. Открывает точную уже имеющуюся строку без поискового debounce. Проверяет статус 404 явно, удерживает реальный GET обновления до проверки очистки и связывает ответ с соответствующим Playwright Request. Сохраняет прежние assertions по длине истории, фокусу, карточке, строке, отсутствию медицинских записей и JavaScript-ошибок. Дополнительно требует очищенные черновики и неизменную идентичность и эпоху сессии.
